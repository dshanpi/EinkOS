# 区分应用 OTA、系统 OTA 与恢复安装

OTA 表示通过网络交付更新，不说明更新范围。EinkOS 的**应用 OTA**更新桌面及用户态组件；**系统 OTA**更新受管理的 Linux 系统组件；**LYNX 全量烧录**用于首次安装或离线恢复。应用支持自动更新，不意味着所在系统已经具备在线整机升级能力。

## 1. 选择正确的升级方式

手机阅读下表时，可在表格区域左右滑动查看各列。

| 对比项 | 应用 OTA | 系统 OTA | LYNX 全量烧录 |
| --- | --- | --- | --- |
| 发布类型 | `application` | `system` | 安装 `system` 发布镜像 |
| 更新对象 | 桌面、内置应用、连接服务、资源、兼容用户态适配 | 经过系统升级方案管理的内核、DTB、rootfs、基础库等组件 | 目标镜像定义的完整系统布局 |
| 常见触发 | 阅读器修复、日历功能、桌面资源更新 | 驱动/ABI 变化、基础系统修复、更新基础设施迁移 | 首次安装、系统无法启动、无法安全在线迁移 |
| 必须匹配 | 系统契约、架构/libc、服务与数据兼容性 | 精确板型/修订、存储/分区、Bootloader、来源系统及当前应用 | 精确板卡、存储、屏幕配置及烧录工具支持 |
| 载荷 | 签名应用清单和目标应用包 | 与选定系统更新器匹配的签名升级载荷及系统资料 | 发布页明确用于 LYNX 的 `.img.gz`，校验解压为 `.img` |
| 写入范围 | 契约允许的应用目录 | 系统方案明确管理的槽位/分区/卷 | 镜像和烧录工具指定的目标存储 |
| 重启影响 | 通常重启相关应用服务 | 通常要重启进入候选系统 | 写入后重新启动整机 |
| 失败恢复 | 回到旧应用及兼容数据 | 由启动链/恢复环境返回旧系统，并处理数据兼容 | 使用电脑、LYNX 和匹配镜像恢复 |
| 用户数据 | 独立保留；迁移必须可恢复 | 数据分区及跨系统迁移需专门保证 | 按会清除数据准备，先做外部备份 |

系统 OTA 与 LYNX 是系统发布的不同安装路径，不是第三条应用版本线。**现有 LYNX `.img` 不等于系统 OTA 包**；没有板级方案时，不把它交给应用更新器，也不直接写入正在运行的根文件系统。

## 2. 当前板卡与系统的边界

当前产品板卡为 `100ask_t113s3-pro`，历史镜像采用 Tina / OpenWrt、NAND `evb1_auto_nand` 和 240×360 EPD。当前仓库提供的是该基线的构建与 LYNX 系统发布流程，没有交付板端系统 OTA、A/B 分区、启动计数回退或系统 OTA 包生成器。

应用自动更新属于已确定的产品架构；要在某个镜像上启用，仍须具备[应用 OTA 基线](APPLICATION_OTA.md)。不能把“应用自动更新”“有 OpenWrt”或“使用 U-Boot”当成整机 OTA 已适配的依据。现有版本的系统更换/恢复继续按[安装指南](INSTALL.md)操作。

## 3. 系统维护者如何接入 OTA

下面是系统 OTA 的工程设计与验收要求，补充说明在线升级需要完成的工作；它不修改既有 DSP-LINUX-001 版本、旧 Release 格式或验收结果。正式实现时需确定并版本化系统 OTA 清单/协议，不直接复用应用清单 schema。

### 明确板卡、存储和恢复机制

选择系统更新方案前，记录 NAND/eMMC/SD 等存储类型、容量、分区或 UBI 卷布局、Bootloader 能力及可用恢复路径。NAND 还需考虑擦除块、坏块、ECC 和 UBI 一致性。不能把面向 eMMC 的槽位写法直接用于当前 NAND 板。

可评估 A/B 系统槽位、独立恢复系统等方案，以及 RAUC、SWUpdate 等成熟框架；它们都是候选方案，不是本项目已采用的组件。A/B 需要空间、启动切换与失败回退共同支持；单槽方案也必须证明断电后能够恢复，不能以“下载成功”作为安全保证。

Bootloader、分区表和信任根应单独定义可更新性及恢复措施。普通系统 OTA 默认只更新方案已经明确支持的组件；无安全迁移链时，通过专门的系统迁移或 LYNX 安装处理。

### 建立系统发布与在线安装的对应关系

系统发布固定预装应用 A0、硬件提交 H、SDK/配置和镜像哈希，保留对应源码与板级验证资料。新系统标签遵循 `system-vS.Y.Z--<board-id>`；既有 `v0.1.0` 保持原有含义。

除系统 Release 的来源、锁定、校验和与验证资料外，在线安装还需绑定以下信息：

| 信息 | 验证目的 |
| --- | --- |
| 板型/修订、存储和布局版本 | 拒绝错误板卡和错误存储目标 |
| 允许来源系统、最低启动链/更新器版本 | 确认设备能执行这条迁移链 |
| 受管组件、槽位/卷、载荷大小和哈希 | 限定写入目标并验证实际写入内容 |
| 系统签名、渠道和升级顺序 | 可信来源、防重放及试用渠道隔离 |
| 新系统契约、预装应用及当前应用处理策略 | 避免系统升级后原桌面无法启动 |
| 数据迁移、启动健康、失败回退和救援方法 | 定义成功条件和不可启动时的恢复路径 |

系统 OTA 与应用 OTA 使用独立的类型判定和授权范围；是否采用独立密钥由威胁模型决定。即使共享信任体系，也不能允许一个应用签名授权写系统分区。完整镜像和 OTA 载荷若同时提供，须记录二者对应关系并分别验证各自安装路径。

### 实现升级事务

1. 验证签名、精确目标和允许升级路径，检查供电、空间及外部备份，取得系统级更新锁。
2. 暂停应用更新任务并确定当前应用处理策略，避免两个更新器同时修改状态或跨越系统契约。
3. 下载并校验载荷，通过板级更新后端写入候选槽位/受管区域，再核验实际写入结果。
4. 持久化升级状态和有限次试启动信息，然后重启进入候选系统。旧可用系统或恢复环境在此阶段仍须可达。
5. 由健康服务验证启动、存储、网络、驱动及 EinkOS 关键功能；在规定观察期通过后确认提交。
6. 启动失败、健康检查超时或掉电中断时，由启动链/恢复系统执行恢复。新 Linux 无法启动时，不能依靠新系统里的用户态程序完成回退。

## 4. 系统升级时怎样处理已经更新过的应用

例如系统 S0 出厂预装应用 A0，设备后来通过应用 OTA 更新为 A1。发布新系统 S1 时，维护者必须选择并验证以下一种策略：

| 策略 | 使用前提 | 安装后记录 |
| --- | --- | --- |
| 保留当前 A1 | A1 明确兼容 S1 的新契约，版本区和数据均保留 | S1 的原始预装身份不变，运行应用单独记录为 A1 |
| 切换到 S1 随附应用 | 随附应用能够读取当前用户数据，或有完整迁移/恢复方案 | 记录实际切换的应用版本及数据格式 |
| 先做应用兼容桥接 | 存在同时兼容 S0/S1 的过渡应用及已验证升级顺序 | 记录桥接步骤，任一步失败时保持一致状态 |

不能安装新系统后默认回到更旧桌面而忽略数据兼容性。系统回退同样要恢复可运行的应用和可读数据；共享数据分区上的不可逆迁移会破坏系统回退，即使 A/B 槽位仍然完好。

## 5. 用户的操作与成功判据

系统 Release 只有明确声明“本板本基线可通过系统 OTA 升级”并给出实际入口时，用户才走在线升级。操作前阅读停机/重启说明、备份数据、接通稳定电源，并确认串口及 LYNX 救援途径。

在设备允许的系统升级入口选择匹配版本，确认安装与重启；等待显示“新系统健康检查通过”的成功终态。下载进度 100%、写入完成、Linux 启动和最终提交是不同阶段。完成后核对系统版本、应用版本、桌面、按键、网络和个人数据。

自动回到旧系统时保留失败记录，不连续强制重试。不能启动时使用该板发布资料里的救援方法，必要时执行 LYNX 恢复。系统 OTA 的无人值守策略须单独获得授权，不继承用户对应用自动安装的选择。

## 6. 放行前必须完成的测试

每个声明目标分别验证：正常升级与重启、错误板型/布局拒绝、签名/篡改/旧清单拒绝、断网恢复、下载/写入/切换/首次启动阶段断电、新内核无法启动、健康超时回退、应用与数据迁移、连续失败限制，以及 LYNX 最终恢复。

结果绑定实际板卡修订、源/目标系统、镜像及 OTA 载荷哈希、启动链版本、时间和日志。只有实际通过的目标才开放对应升级路径；应用 OTA 通过不能替代系统 OTA 验证。
