# DSP-LINUX-001：Linux 开发板开源、版本关联与发布规范

规范版本：**1.0.0**。适用范围：dshanpi Linux 开发板的用户态软件及配套系统镜像。
“必须”是交付门禁，“建议”可按项目判断；不适用项必须有板卡能力说明及理由。
本规范规定交付方式，不强制所有板使用 LVGL、Tina、OpenWrt、墨水屏或相同 CPU 架构。

## 1. 仓库与代码边界

| 编号 | 位置 | 必须负责的内容 |
| --- | --- | --- |
| R01 | 应用仓库，例如 dshanpi/EinkOS | 桌面/应用、连接服务、用户态适配、运行配置、测试、UI 截图、使用/架构/开发文档、发布工具及版本记录 |
| R02 | 对应板卡原硬件/SDK 仓库 | 内核驱动、设备树、Bootloader、板级配置、硬件诊断、系统集成配方及镜像构建 |
| R03 | 应用仓库 Releases | 每版应用源码、各支持板 `.img.gz`、校验和、版本锁、构建/SDK/验证记录及版本说明 |
| R04 | dshanpi/lynx-releases | LYNX 安装及烧录工具的统一获取入口 |

应用源码只保留一个维护入口。硬件配方通过固定应用提交及源码归档 SHA-256 获取应用，
不得复制一套长期独立维护的应用，也不得从浮动分支获取发布输入。
应用自带的服务/默认配置归应用仓库；板级选择、依赖、分区和打包逻辑归硬件仓库。
如果现有厂商 SDK 仓库不能公开，硬件覆盖层必须说明基线及完整对应源码的获取方式。
原有第三方许可证和来源声明必须保留；产品自有代码许可证由项目明确，不能把整个 Linux
镜像统一改成应用的许可证。固件和编译产物进入 Release，不进入源码 Git 历史。

## 2. 板卡配置与支持范围

**B01** 每块板必须有版本受控的 `board-profile.json`，包含稳定 board_id、硬件修订、SoC、
架构、存储、显示/输入、网络能力、SDK 基线、构建目标、工具链及安装/恢复说明。
`board_id` 使用小写字母、数字和连字符；存储布局或显示变体不能混用镜像时，分别分配 ID。
板卡 profile 的版本和 SHA-256 必须写入每次发布锁。

**B02** 板卡状态明确区分计划、适配中、预发布和已验收。README 只列已实现和已验证能力。
不同板不共享未经验证的电源、分区、显示、网络、启动或烧录结论；只有命令行的设备可以
注明无 UI，不应编造截图。硬件缺少某功能时用能力矩阵和不可用行为说明。

**B03** 安装统一指向 [LYNX](https://github.com/dshanpi/lynx-releases)。记录实际测试的 LYNX
版本、主机系统、板卡模式及恢复步骤。新板若未被 LYNX 支持，先完成工具适配；可以保留
开发草稿，不能提供声称可用的公开安装流程。此规则不要求把系统镜像放入 LYNX 仓库。

## 3. 不可变的版本关系

**V01** 一个发布版本锁定：

```text
应用标签 → 应用完整提交 A → 带 A 的应用源码包
硬件标签 → 硬件完整提交 H → 系统集成配方 → 同一个 A + 源码归档哈希
SDK 基线 → 每个组件的完整提交/源码哈希 + 已归档补丁/配置/额外文件
板卡 profile + 工具链 + 构建命令 → 实际镜像 → SHA-256 → 本镜像的验证证据
```

分支用于开发定位，标签和完整提交用于发布。分支最新提交可以前进，已发布标签必须保持
指向不变。Git 对象 ID 记录完整值，不截断；非 Git 输入记录可获取位置和文件 SHA-256。
不同仓库的提交号本来就不同，一致性是指上述引用关系一致。

**V02** 应用标签默认 `vX.Y.Z`；新板硬件标签默认 `<product>-vX.Y.Z--<board-id>`。
现有固定标签可保留，但必须在锁文件中明确记录。一个多板 Release 共享一个应用版本/提交，
每块板分别锁定硬件、SDK、配置和镜像。不同应用提交使用不同 Release，不能共用版本号。
如果只修改系统配置或硬件，也必须发布新版本并记录实际应用提交，不能替换旧版本镜像。

**V03** `release-lock.json` 必须绑定源码、板卡配置、SDK 清单、build-info 和每个镜像的
文件名及 SHA-256；同时记录压缩镜像与解压后镜像的哈希。`validation` 绑定解压镜像哈希。
文件内容与锁的哈希不符、硬件配方引用不同应用、远端标签不符，必须阻止上传/公开。
锁文件自身不包含自身哈希，交由 `SHA256SUMS` 覆盖；SDK/构建记录不反向依赖锁，避免循环。

**V04** 构建后生成的锁和证据可以提交到晚于 A/H 的文档提交；应用标签仍指 A，硬件标签仍指 H。
不得为追求“所有文件在同一提交”而篡改镜像来源。SDK 多仓库项目必须逐项固定提交；只写
“Tina/Yocto/Buildroot 某版本”或仓库名、只列修改文件路径，不构成完整复现输入。

## 4. 构建与来源证据

**C01** 构建记录必须包含实际工具链/宿主环境或构建容器摘要、目标配置、命令、构建日志引用、
应用 A、硬件 H、SDK 清单及时间。涉及目标二进制必须完成该架构的交叉编译和系统打包。
必须核对实际打包镜像中的应用标识与 A 相符；仅检查暂存 rootfs 或文件时间戳不够。

**C02** 应用与硬件发布输入应为已提交的干净树。SDK 本地修改、未跟踪源码、厂商额外文件、
配置与补丁须逐项归档并记录哈希及应用顺序；构建缓存/产物列入明确排除规则，不能忽略所有
未跟踪文件。没有必要公开个人凭据，但凭据不得成为构建输入包的一部分。
公开发布必须具有完整对应源码和厂商组件说明的可获取证据；应用源码包不能替代系统源码。

**C03** 发布配套 `.img.gz`，gzip 不携带宿主原始路径，建议固定 mtime 以便核验。
声明可复现时区分“可用相同输入重建功能镜像”和“逐字节可复现”，后者必须有重复构建对比证据。
大于单个附件限制时先解决分发方案并记录规范修订，不能把应用压缩包充当系统镜像。

## 5. 每版交付物

| 编号 | 必需交付 | 单板或多板约定 |
| --- | --- | --- |
| A01 | 应用完整源码包 | `<product>-v<version>-source.tar.gz`，包含实际应用版本、提交标识和许可证 |
| A02 | 配套系统镜像 | 每板 `<product>-v<version>-<board-id>.img.gz` |
| A03 | `release-lock.json` | 顶层应用信息、规范版本及各板硬件/SDK/资产对应关系 |
| A04 | `build-info-<board-id>.json` | 逐板构建记录 |
| A05 | `sdk-manifest-<board-id>.json` | 逐组件源码身份、覆盖层、补丁、配置和额外输入 |
| A06 | `validation-<board-id>.json` | 与实际镜像哈希绑定的检查结果和证据 |
| A07 | `board-profile-<board-id>.json` | 本次实际板卡配置，锁内记录版本和哈希 |
| A08 | `SHA256SUMS` | 覆盖所有下载附件，唯一例外是自身；不得使用同名附件覆盖不同板记录 |
| A09 | Release 说明 | 支持板清单、应用/硬件固定链接、SDK、安装入口、验证范围及已知问题 |

关联的完整系统源码、补丁和第三方说明可以放在可公开获取的外部固定地址，但必须锁定
其内容身份，验证可获取且与本镜像对应。放在本 Release 的额外附件也必须纳入 SHA256SUMS。
历史单板格式可通过明确的适配映射保留，本规范不允许重写旧公开资产来“升级格式”。
模板字段和命名细则见 [CONTRACT](CONTRACT.md)。

## 6. 发布门禁

| 编号/项目 | 草稿 Draft | 公开 Pre-release | 正式 Stable |
| --- | --- | --- | --- |
| G01 交付资产完整，身份和哈希一致 | 必须 | 必须 | 必须 |
| G02 远端应用/硬件标签及配方核验 | 必须 | 必须 | 必须 |
| G03 逻辑/工具测试、独立源码构建、目标构建、系统打包、镜像内容核验 | 记录实际结果 | 全部通过 | 全部通过 |
| G04 SDK 对应源码、修改内容及厂商分发说明 | 可待补 | 完整且有审核证据 | 完整且有审核证据 |
| G05 核心硬件：LYNX 烧录、启动、存储/分区、恢复路径 | 可 not_run/failed | 可 not_run，必须已具备明确 LYNX 支持；不能有 failed | 全部 passed |
| G06 按板能力：显示/输入、应用状态恢复、网络、时间、可选外设/降级 | 可 not_run/failed | 可 not_run，不能有 failed | 适用项全部 passed |
| G07 文档/截图/安装说明与实际行为一致 | 必须 | 必须 | 必须 |

检查状态使用 `passed`、`failed`、`not_run`；可选硬件项允许 `not_applicable`，必须关联
profile 中缺失的能力并说明理由。核心构建/身份检查、启动、LYNX 烧录及恢复检查不得跳过。
不适用项在选板配置时确定，不能在失败后改成不适用；“无蓝牙时正确降级”仍是一项实际测试。
证据必须记录镜像哈希、测试环境、测试者、日期和日志/观察结果，不能只填 passed。
模板里的字段、CI 截图、通过的编译均不是实机验收证据。

多板 Release 的公开状态以声明支持的全部板共同通过为准。不能用 A 板的结果替代 B 板。
缺项板可从本版支持范围移除并在下一版加入；必须同时移除其资产/支持声明，不能藏在正式包中。
公开后资产及支持矩阵冻结；改变镜像或新增板型发布新版本。未改镜像的后续验收可通过
附加可追溯报告和新修订发布说明记录，不能静默覆盖旧验证文件。

## 7. README、截图、架构和开发要求

**D01** README 必须提供项目定位、明确板型/状态、全部已实现 UI 页面与主要成功/失败状态、
功能及限制、架构/进程/接口说明、构建入口、版本对应表、安装入口、仓库边界和许可证链接。
**D02** 截图必须来自真实 UI 代码或设备，区分主机渲染与实机拍摄；使用演示数据，记录源码
来源及复现方法。每次 UI/字体/网页修改更新截图并检查裁切/缺字。无 UI 的项目明确说明。
**D03** 开发文档与 AGENTS/Skill 必须说明应用和板级边界、API/ABI/配置迁移、目标工具链、
检查命令和实机验证要求。自动化不得伪造 passed、移动发布标签或替换已公开资产。
Skill 只指导用户已授权的工作，不自动授权烧录、公开发布或修改无关仓库/全局配置。

## 8. 执行顺序与责任

应用维护者确定 A；板级维护者固定配方并确定 H；构建者保存 SDK 输入和生成镜像；
验证者对实际镜像记录结果；发布维护者核对来源与远端实际附件，再变更发布状态。
小团队可由同一人承担多项职责，但证据与责任记录必须保留。

流程按 [接入检查表](ONBOARDING.md) 执行。公开前重新下载实际 Release 附件校验，避免
只检查本地副本；远端写入发生不明确失败时先查询状态再补传，不重复创建或覆盖公开文件。

## 9. 版本维护与当前实现

本规范版本独立于产品版本；发布锁记录 `standard.id` 与 `standard.version`。
新规范放到新目录，项目明确迁移，不能追溯宣称旧版本满足新规范。
首个实例是 [T113 v0.1.0](examples/T113.md)：现有标签、镜像和单板资产保持不变，
但完整 SDK 修改归档和实机验收尚未完成，所以仍是草稿。

当前 EinkOS `scripts/release.py`、`check_release.py`、`version_lock.py` 是 T113 专用实现，
其旧 schema_version=1 不等于本通用规范的 schema。新板需要实现 profile/SDK/打包/验证适配，
并通过身份错配、镜像篡改、标签漂移和缺项门禁测试。不能仅修改常量或 board_id 宣称已经支持新板。
本目录的模板与检查表是可复用规范，不是已交付的任意板全自动发布引擎。
