# DSP-LINUX-001 / 1.1.0：应用更新与系统镜像双发布线

本版记录用户确认的架构：**Linux 底层及接口稳定，EinkOS 独立开发、独立发布应用升级包，
设备从 EinkOS GitHub Releases 获取兼容更新。** 只有修改底层系统时才发布新系统镜像。

本版继承 [1.0.0](../v1.0.0/SPEC.md) 的仓库边界、来源记录、真实证据及不可变发布原则，
但替代其中“每次软件发布必须带系统镜像、同步硬件版本”的要求。
1.0.0 的 SDK 锁定、镜像构建、LYNX 烧录和逐板镜像资产门禁仅用于本版的 system 发布。
应用发布按本页的 application 门禁执行，不重复要求未改变的底层构建和整套 SDK 审核。

## 1. 发布分类是第一道门禁

| 编号 | 发布类型 | 允许改动 | 必需交付与安装方式 |
| --- | --- | --- | --- |
| T01 | `application` | 桌面、应用、连接服务、字体/资源、应用私有依赖和兼容的用户态适配 | 应用源码、升级包、兼容/更新清单、构建/验收记录、校验和及签名；设备更新器安装 |
| T02 | `system` | 内核、驱动、设备树、Bootloader、分区、基础库、系统服务契约、系统接口或升级基础设施 | `.img.gz`、完整版本锁、SDK/构建/板卡/验收资料和对应源码；LYNX 安装 |

**T03** 每个 Release 清单必须显式写 `release_kind`，不能仅凭标题、文件后缀或 GitHub 的
“Latest”判断类型。未知类型拒绝处理，application 更新器不得安装 system 附件。
一个 Release 只承载一种类型；新应用默认标签 `app-vX.Y.Z`，新系统默认
`system-vS.Y.Z--<board-id>`，两条版本线独立递增。既有 `v0.1.0` 和硬件标签作为历史系统版本保留。

**T04** 纯应用发布不要求新的硬件提交、硬件标签、SDK 构建或 `.img.gz`。应用提交 A 是应用发布的
真实来源。已安装的系统仍保留原镜像的 H/SDK/预装应用 A0；在线更新后的应用 A1 单独记录，
不能把 A0 或旧镜像 build-info 改写成 A1。系统修订可继续预装同一应用版本，不强制应用升版。

**T05** 若应用需要更改 ioctl/驱动 ABI、系统基础库、启动/分区、设备权限或基础服务约定，
必须转为系统发布或依赖已另行发布的新系统基线。不得把底层补丁藏进“应用升级包”。

## 2. 系统契约与应用兼容性门禁

**K01** 首个支持在线更新的系统镜像必须提供可读取、归系统管理的系统身份/接口契约，
建议路径 `/etc/einkos/system-release.json`。它记录系统版本、构建标识、board_id/硬件修订、
架构及调用约定、libc/加载器、系统 API/EPD ABI、必需运行库/服务能力、更新器版本与受管应用目录。
安装在镜像内的契约不写该镜像或构建后发布锁的哈希，避免自引用；构建后由外部系统发布锁
将镜像 SHA-256 与契约 SHA-256 关联，设备通过固定系统标识定位此记录。
同一接口家族只有在兼容性经过验证时才能保持版本；破坏兼容的变更必须升级契约版本。
契约版本号不能代替契约定义或实际验证。模板见 [system-contract](templates/system-contract.json)。

**K02** 应用清单必须声明目标架构/ABI、适用板型或适配后端、支持的契约版本集合、必需依赖、
最低更新器版本、可从哪些应用版本升级，以及数据格式和回退兼容条件。不同目标构建分别列出
包名、大小、SHA-256 和测试记录。即使 CPU 名称相同，也不能忽略 libc、浮点 ABI、显示及服务差异。

**K03** 设备在安装前对照本机契约检查全部条件；缺字段、未知版本、不匹配或没有升级路径时
拒绝安装，并说明所需基线。不能仅比较应用版本大小，也不能先装上再靠启动失败判断兼容性。
发布验收绑定实际测试的系统 Release、镜像哈希和契约文件哈希；不得宣称支持未验证的整个版本范围。

**K04** 应用日常兼容目标是“系统契约”，不是每次跟随硬件分支最新提交。已有系统来源和审核
证据通过不可变系统 Release/锁/哈希复用；新增应用及其随包依赖仍须提供对应源码和来源说明。
若依赖的系统仍未具备公开安装条件，不能宣称它已经构成公众可用的自动更新基线。

## 3. 应用升级包及设备更新门禁

| 编号 | 必须约束 |
| --- | --- |
| U01 来源与完整性 | 设备验证可信签名及文件大小/哈希。签名覆盖发布身份、渠道、兼容条件、包清单和包哈希；只把包与 SHA256SUMS 放在同一下载处不能证明来源。信任根由系统预置或可信迁移建立，禁止从同一未验证下载中临时信任公钥。 |
| U02 写入边界 | 包文件与安装操作只进入系统契约声明的应用受管范围。拒绝路径穿越、越界链接和特殊文件；不得写原始块设备、内核/模块、设备树、Bootloader、分区表、系统契约、信任根或替换系统基础库。安装钩子也受同样约束，不能只扫描文件名。 |
| U03 事务安装 | 下载和校验完成后暂存，确认磁盘空间、安装锁和依赖；有序停止相关应用/连接服务，再原子切换版本。中断、断电、重复触发不能留下半安装状态，重启后能够恢复旧版或完成一致状态。 |
| U04 健康与回退 | 明确健康检查、观察时间及失败条件；验证新进程、关键 IPC、状态读取和目标基本功能。失败自动回到已知可用版本，不仅检查进程是否存在；保留回退所需旧包和状态，限制反复失败重试。 |
| U05 用户数据 | 书籍、阅读进度、书签、网络及用户设置独立于版本目录。更新不得清空或随包覆盖。数据迁移可验证、可恢复，代码回退与数据回退一致；不可逆迁移且无恢复方案时禁止无人值守更新。 |
| U06 更新选择 | 只选择可信、类型为 application、与设备兼容且属于用户允许渠道的发布。默认稳定渠道；预发布需要明确选择，草稿不进入更新源。系统版本、其他架构包和来源不明记录不得进入候选。 |
| U07 防重放与重试 | 声明升级顺序及已接受版本，拒绝未经允许的旧远端清单/降级。故障恢复到本机已知良好版本不等于允许远端随意降级；记录失败原因并避免无限自动重装。 |
| U08 自更新边界 | 更新器自身/信任机制单独定义兼容和恢复路径；没有通过专项验证前，经系统镜像发布更新，不与普通应用载荷混合替换。 |

这些是发布与实现约束，不表示更新器已经实现。具体打包格式、签名实现和进程管理适配必须
在实现时选定并验证；不能靠填写 `passed` 或设置 `auto_update_eligible=true` 让尚不存在的能力通过。

## 4. 应用发布资产

必须有应用源码包、各目标 `EinkOS-app-v<version>-<target>.tar.gz` 升级包、
`application-release.json`、对应可信签名、`application-build-info.json`、
`application-validation.json`、SHA256SUMS 和版本说明。
清单必须绑定应用完整提交、实际应用版本、源码/目标包/构建/验收文件的哈希。
签名覆盖清单原始字节，清单不包含自身及自身签名的哈希，SHA256SUMS 覆盖二者，避免循环。
记录采用规范 1.1.0；不要求附新 `.img.gz`、新硬件标签或复制未改变的 SDK。
[应用清单模板](templates/application-release.json) 与 [应用验收模板](templates/application-validation.json)
中的 null、not_run、空兼容集合均不是可发布值。

系统发布继续使用 1.0.0 的逐板镜像资产与来源门禁，并新增 `release_kind=system`、系统契约、
预装应用版本及更新器能力记录；首次引入在线更新时必须验证镜像到首次应用升级及失败恢复的完整链路。
LYNX 只负责系统安装/恢复，普通应用更新不要求用户反复烧录。

## 5. 两条线分别执行门禁

| 门禁 | 应用 Draft | 应用 Pre-release | 应用 Stable / 默认自动更新 |
| --- | --- | --- | --- |
| 分类、提交/源码/包身份、资产校验 | 完整一致 | 完整一致 | 完整一致 |
| 编译、逻辑/工具、包边界、应用来源审核 | 如实记录 | 全部通过 | 全部通过 |
| 兼容拒绝、签名/篡改拒绝、事务安装、断电恢复、失败回退、数据保护、防重放、渠道隔离 | 可 not_run/failed | 全部通过，不允许跳过更新安全性验证 | 全部通过 |
| 目标系统及更新器 | 可待接入 | 已具备可公开使用的基线，完整更新链路已验 | 已验收基线，完整更新链路已验 |
| 功能回归 | 如实记录 | 可披露非关键功能未测项，不能有已知失败项 | 所有声明支持项通过 |
| 面向设备 | 不进入候选 | 仅明确选择预发布渠道的兼容设备 | 满足以上门禁且明确获准自动更新的兼容设备 |

系统 Draft/Pre-release/Stable 仍执行 1.0.0 的系统构建、来源、镜像核验及 LYNX/硬件门禁。
**任何类型都不能用另一类型的证据替代自身门禁。** 一板/一架构通过不代表其他目标通过。
稳定版本并不自动获得静默安装权限；设备的检查/提示/自动安装策略应由产品设置明确决定。

每项必须有测试者、时间、目标包哈希、测试系统镜像/契约身份和日志/观察记录。
公开前重新下载远端真实附件核对应用标签/提交、清单签名及全部包哈希。
附件和标签公开后冻结，修订应用或系统分别发布对应线的新版本；不能覆盖旧包绕过版本检查。

## 6. 工作流程与阻断条件

应用线：确定兼容系统 → 提交应用 A → 测试/目标编译 → 制作升级包 → 在声明基线上验证升级及回退 →
生成签名清单/来源/验收记录 → 应用草稿 → 下载远端附件复核 → 应用预发布或稳定发布 → 兼容设备更新。

系统线：固定预装应用 A0、硬件 H、SDK/配置 → 构建镜像 → LYNX/实机验证 → 保存系统契约及来源 →
镜像草稿 → 复核 → 系统发布。系统一旦稳定，多个后续应用版本可以复用这一基线。

出现以下情况必须停止应用公开/自动更新：接口不兼容、未知系统身份、未实现签名验证、
写入边界越界、安装/断电恢复/健康回退未验、用户数据会丢失、目标基线未公开可用、验证证据缺失。
修复或转走系统线，禁止通过伪造结果、放宽兼容集合或更改 release_kind 绕过。

## 7. 当前状态与工具边界

当前 T113 v0.1.0 仍是历史系统草稿，原始镜像/标签/硬件和 SDK 记录保持不变。
当前 `release.py` / `check_release.py` / `publish-release.sh` / `promote-release.sh` 仅实现旧 T113
系统线门禁，不是本应用更新协议的实现。不得把应用包塞进旧系统发布流程或声称设备已支持 OTA。
应用打包、签名、设备更新器、系统契约和对应自动化门禁都需后续实现及验收。
本次交付是可执行审查依据和发布约束记录，不生成升级包，也不修改已有镜像。
